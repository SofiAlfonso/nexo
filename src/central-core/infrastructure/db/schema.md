# D2 — PostgreSQL 16

`createD2Pool(env?)` accepts `D2_DATABASE_URL` first, or all five `CENTRAL_POSTGRES_HOST`, `CENTRAL_POSTGRES_PORT`, `CENTRAL_POSTGRES_DB`, `CENTRAL_POSTGRES_USER`, `CENTRAL_POSTGRES_PASSWORD` settings from `config/examples/`. `D2_POOL_MAX` is an optional positive integer (default 10). The caller owns `pool.end()`. Call `await migrate(pool)` before serving C4. The runner loads numbered `.sql` files relative to its module, holds a D2 advisory session lock, and applies each migration and its `public.d2_schema_migrations` entry atomically. It verifies SHA-256 on subsequent runs. Keep the SQL files beside the module in deployed builds; never edit an applied migration.

Checksums normalize line endings to LF. Previously applied SQL with identical CRLF content is verified before its tracking checksum is upgraded to LF; any other content change remains an error.

`001_initial.sql` creates `m1_config_permisos` (client, venue, event, zones, points, readers, versioned tickets/permission changes and policies), `m2_evidencia` (idempotent batches and evidence, decisions, latest point/coordinator state, per-minute counts, incidents/actions, immutable audit log), `m3_conciliacion` (close and differences/resolutions), `m4_liquidacion` (contract and settlement), and `auth` (operators and sessions). Times are `timestamptz`, amounts are `numeric`, and foreign keys are scoped by event where applicable. D2 only observes decisions made by C2; it cannot authorize admissions. Do not store ticket buyers or plaintext passwords. Seed operator passwords must be hashed with argon2 outside SQL; no default credentials are provided. `auth.sesiones.id` should be an opaque random token identifier (prefer storing a digest, not the cookie token).

`002_contrato_eventos.sql` allows one agreement to cover multiple events through `m4_liquidacion.contrato_eventos`. The idempotent `seed/seed.sql` is run with `psql --set=operator_password_hash=<argon2 hash>` after migrations. It creates the prototype pilot's three events, one shared contract, 20 readers/points, and 16,240 version-1 tickets for the active event. Re-running it leaves operator password hashes unchanged.

`003_recinto_capacidad.sql` records venue capacity (the pilot stadium has 20,000 seats). The historical paid event has a closed event and collected liquidation; the current paid event is open; the future free event is in preparation. The pilot advance, costs and free-event cost ceiling live in the contract's `condiciones` JSON.

The reader fixture JSON is exported from authoritative **D1**, not this D2 replica: `seed CLI --export <ruta>` writes `eventos[]` (tickets with code, zone, validity and consumption), `lectores[]` (reader/point/event and allowed zones), and `casos[]` covering valid (`TA-8800-0000`), annulled (`TA-8800-0001`), used/duplicate (`TA-8800-0002`), wrong-zone (`TA-8804-0980`), unknown (`TA-DESCONOCIDA`), and concurrent copies (`TA-8800-0003` at P-01/P-02). See `deploy/scripts/export-boletas.ts`; D2 only mirrors the same ticket permissions for reporting.

Deduplicate batches on `m2_evidencia.lotes.id_lote` and records on `m2_evidencia.evidencias(evento_id, tipo, id_origen)`; compare `contenido_hash` before treating a collision as a retry. Commit a batch, its evidence, derived state, and stored `acuse` together. `m2_evidencia.bitacora` rejects both updates and deletes; write new rows for corrections. Retain business evidence for at least 90 days; no automatic deletion is configured. No RLS is installed in this laboratory PoC (ADR-009); application code must scope reads and writes to the authenticated event/client.
